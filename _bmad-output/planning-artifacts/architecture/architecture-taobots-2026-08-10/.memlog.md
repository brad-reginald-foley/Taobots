- (decision) Chi is TWO TIERS. Tier 1 = chi pool: raw, mixed, volatile; what eating deposits; co-present incompatible elements degrade each other here (CHI-4, deferred). Tier 2 = per-element buffers (meridians; LegPart.reserve is an early instance): single-element and therefore stable. Binds: all chi consumers/producers. Prevents: a second, incompatible storage idiom appearing when E3 lands, and Ke degradation being applied at the wrong tier. Source: Brad's domain model, 2026-08-10.
- (decision) Today's TaobotSimple.storage conflates both tiers because meridians do not exist. It is designated the POOL tier. At E3 the meridian buffers separate out of it. Binds: E1, E2, E3 stories. Prevents: new code treating storage as a per-element stable buffer and then breaking when the tiers split.
- (decision) The part/organ <-> chi seam is a PORT: request(element, amount) -> granted, and deposit(element, amount) -> accepted. Consumers never mutate a chi dict directly. ChiPool implements the port now; MeridianNetwork implements it at E3 while sitting on the pool. Binds: every body part, every organ drain, collection, and conversion. Prevents: callers coupling to the pool's data shape, which would make E3 a rewrite instead of a substitution.
- (decision) A denied request is legitimate behavior, not a bug. At E3, request() may return 0 because the bot has no meridian of that element. This is the intended selection pressure (body plan must match diet) and must be documented so it is not 'fixed' later.
- (decision) Conversion (element -> element, respecting CYCLE_EFFICIENCY) is a capability OF THE CHI TIER, not of TaobotSimple. It lands on ChiPool now and is inherited/hosted by MeridianNetwork at E3 (MER-14). Consistent with E1-S2's existing requirement to implement it as a separable function rather than inline in _cycle_elements.
- (constraint) Staging agreed: B (ChiPool object owning the ledger) now, C (demand/settle economy hosted by the meridian network) at E3. The port seam is what makes C a policy swap rather than a rewrite.
- (decision) An ORGAN SYSTEM is the set of parts of one element type; the organ value is a DERIVED summary statistic over that set, not stored state. Prevents: double-bookkeeping between part integrity and organ integrity, and organ scalars going vestigial when their epic lands (as organs[WATER] already did).

- (decision) THE LAW TEST (Brad's criterion, supersedes 'could a mutation change this'): a number is a LAW if making it evolvable would let organisms escape a constraint the simulation exists to impose. Conversion efficiency, elemental degradation, metabolic cost per unit of work are laws - if evolution can touch them it simply evolves super-efficiency and the elemental economy stops creating pressure. Laws are exogenous.
- (decision) FOUR HOMES for tunables. (1) Laws -> configs/laws.json, shared by every world config; an arena may deliberately override named entries (fire_arena degrade_rate 0.002 vs 0.001 is the legitimate case) but must not drift by accident. (2) Environment -> per world config: size, population, spawn counts, densities. (3) Traits -> genome/organism spec: anatomy, part counts, positions, per-part params; evolvable. (4) Module constants -> structural invariants only (e.g. ORGAN_MAX as a scale unit). Prevents: Phase 2 exit criterion 1 being unevaluable (organ settings are currently module constants global to every bot, so two bots cannot differ in them) and Phase 4 being unable to evolve anything held in module scope.

- (decision) OBSERVERS NEVER MUTATE THE SIMULATION. Today WorkshopLogger.log_tick and RunLogger.on_tick read taobot._interval_damage/_interval_resources (private) and call taobot.reset_interval() - so the meaning of the interval accumulators depends on which observer is attached and how often it runs, and they grow unbounded with logging off. The organism accumulates its own per-tick deltas; observers read and compute their own intervals. Prevents: the simulation not being independent of its observers, which under the determinism goal makes 'identical state' and 'identical logs' come apart.
- (decision) SNAPSHOT CONTRACT: anything that PERSISTS OR TRANSMITS state (loggers, inspector, genome export, future arena/game layer) consumes a get_state()-style snapshot, never live simulation objects. Read-only live access for bulk rendering is explicitly allowed - building a full snapshot per bot per frame to draw circles is waste. The line defended is mutation and persistence, not reads. Makes PLAN.md's 'visual design pass without touching simulation logic' and the arena layer consumers of a contract rather than forks.

RESERVED, not built: a phase may later carry a period (Phase 3 runs neurons every 6 ticks), so no epic may assume 'my code runs exactly once per tick' in its accounting.
